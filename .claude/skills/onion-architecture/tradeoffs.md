# Tradeoffs — where credible sources disagree

Three decisions in [SKILL.md](SKILL.md) are contested **between primary sources**,
not between good sources and blog spam. Each is recorded here with the argument
on both sides and what we chose, so the rule can be challenged on its merits
rather than re-litigated from scratch.

## 1. A repository over an ORM

**For.** Palermo puts repository *interfaces* in the first ring out from the
domain as a defining feature of Onion: the core declares how objects are saved
and retrieved, infrastructure implements it. Fowler's Repository gives the
collection-like interface. Martin's Dependency Rule is blunter and more directly
applicable — nothing in an inner circle may name anything in an outer one,
*including data formats* generated by an outer layer. A Drizzle `$inferSelect`
row is exactly such a data format.

**Against.** Ayende's classic argument is that an ORM session already *is* a
collection-like abstraction, so wrapping it adds code without value: query reuse
is largely a myth, and the wrapper hides the ORM's capabilities so performance
tuning becomes architectural surgery. Freestone makes the same case naming
Drizzle and Kysely specifically, and adds that mock-based repository tests give
false confidence now that container-backed integration tests are cheap. Bogard's
Vertical Slice critique targets the ceremony: "Controller MUST talk to a Service
that MUST use a Repository" fits a minority of real requests. Seemann supplies
the sharpest test — a typical `IRepository` mixing query/insert/update/delete
supports neither a Composite nor a Null Object, so it is a *test seam*, not an
abstraction. And Drizzle's own maintainers state the core is deliberately not a
repository layer and will not become one.

**What we chose.** Keep `repository.ts`, but justify it on the narrow ground that
survives the critique: **it is the seam that keeps the persistence model out of
the application layer.** That is not speculative here — `reviews/service.ts` and
`reviews/run-executor.ts` import `db/rows.ts` today, so a column rename is
currently an application-layer change. The repository earns its place by fixing a
measured problem.

What follows from choosing that ground:

- A repository is a **thin data-access module**, not a collection abstraction. No
  Specification DSL, no class-per-`where`-clause, no pretence that we could swap
  Postgres out.
- It may use the full Drizzle query builder internally, including relational
  queries and prepared statements. Hiding Drizzle's power was never the goal.
- It returns **contract types**, and that single output rule is what the boundary
  is actually for.
- A richer port is justified only where there is a real aggregate invariant to
  protect. We have none yet.

## 2. Unit-of-Work typing

**For a domain-facing port.** The pure form is a hand-written
`ITransactionManager` — `startTransaction<T>(cb: (tx: ITransaction) => Promise<T>)`
— so no Drizzle type ever appears in a signature the application layer reads. The
Sentry write-up implements exactly this for Drizzle + Clean Architecture, with
repositories taking an optional `tx`.

**Against.** The `tx` type is the hard edge of the whole question: even the
version-proof community derivation
`Parameters<Parameters<typeof db['transaction']>[0]>[0]` is still a Drizzle type.
An abstract port hides it but adds a layer whose only job is hiding — the exact
shape Three Dots Labs names as the top overengineering signal, and the exact
"interface with one implementation" Seemann warns about.

**What we chose.** Add `Tx` and `DbOrTx` to `db/client.ts`, type repositories as
`DbOrTx`, and open the transaction in the service. Reasons, in order:

1. Services here already depend on `Db` transitively through the Container, so
   the abstract port would be hiding a dependency that is not actually hidden.
2. It is one type alias and zero new layers, versus an interface pair plus an
   implementation for a single database we have no plan to change.
3. The urgent problem is not purity, it is that **there are no transactions at
   all**. `repo-intel/repository.ts` does `delete`-then-chunked-`insert` in three
   methods with none, so a crash leaves the index empty. Ship atomicity first.

Revisit if a second persistence technology ever appears — at that point the port
stops being speculative.

## 3. Layers are not the top-level folders

**The temptation.** Most Clean-Architecture write-ups put `domain/`,
`application/`, `infrastructure/` at the project root. It is the most visible
expression of the Dependency Rule and it looks tidy.

**Why we don't.** Fowler's caveat is explicit: layering is valuable for narrowing
attention, but once a system grows, "split your top level into domain oriented
modules which are internally layered." Uncle Bob's own Screaming Architecture
says the top directory should announce the domain, not the technique, and North's
CUPID Domain-based property says the same from a critic's angle.

`server/src/modules/<domain>/` already is that shape, with layers *inside* each
module (`routes` / `service` / `repository` / `helpers`). The risk this skill
guards against is someone "improving" it by hoisting the layers to the root.

**What we chose.** Domain modules at the top, layers inside. `src/adapters/` and
`src/platform/` are the deliberate exceptions: they are genuinely cross-domain,
and splitting them per module would duplicate them.

## 4. A tension we are *not* resolving yet

`platform/errors.ts` `AppError` carries a `statusCode`. That is an HTTP concept
living in a type the application layer throws — transport leaking inward.

Two defensible options: legalise it as a pragmatic exception (the API is the only
consumer, and the alternative is a mapping table that mostly restates the error
name), or map domain errors to status codes in the transport layer's error
handler.

It is recorded, not decided. Don't let a review silently pick one side.
